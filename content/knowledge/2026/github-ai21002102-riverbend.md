# Riverbend

## 一句話介紹

Riverbend 不是可直接安裝的框架或套件，而是一套從自架 AI 伴侶系統實戰蒸餾出的長期記憶方法論：它把「每次模型醒來該看到什麼、什麼只在需要時取回、什麼應該沉底保存」拆成可操作的架構與判準，目標是在跨視窗、上下文壓縮與長期互動下維持角色與事實的連續性。

## 它解決什麼問題

長期 Agent 的難題通常不是「資料有沒有存下來」，而是**有限上下文裡該讓模型注意哪些資訊**。如果把所有歷史都常駐，每輪成本會持續膨脹，舊語氣與舊狀態也可能把模型拖回過去；如果只保留很少內容，跨視窗後又容易失去人物、關係、近期事件與既有決策。

Riverbend 的核心論點因此是「記憶不是儲存問題，而是注意力問題」。它不試圖用單一向量資料庫解決所有事情，而是先把資訊按使用頻率與權威性分層，再決定哪些內容要推送、哪些內容要檢索、哪些內容只需完整保存。

另一個實際問題是多視窗並行。剛剛在另一個房間發生的事，如果也丟進全庫檢索，會和數週前的內容平權競爭，而且使用者轉述時常會換句話說，純檢索未必找得到。Riverbend 因此把「近況」和「回憶」分流：近期跨視窗動態用熱橋直接推送，更早的歷史才交給召回系統拉取。

它也處理長期記憶最容易被忽略的風險：來源歸屬錯誤、把歷史當現場、模型被自己的舊台詞牽著走、摘要與原文互相污染，以及記憶子系統故障後反過來阻斷正常對話。

## 核心概念

第一個核心是**三層記憶架構**：

- **睜眼層**：每輪都要看到的少量內容，例如人格、行事方式、必要硬事實與當日狀態。這一層的設計目標是持續瘦身，而不是一直累積。
- **召回層**：按需取回歷史片段，負責真正的「回憶」。來源實作使用 BM25 與向量檢索並行，再經候選擴展、結構過濾與小模型裁判決選。
- **書庫**：完整保存但不常駐上下文的日記、歸檔對話與退潮記憶。遠期內容的重點不是繼續壓縮，而是保留原文並確保找得到。

第二個核心是**賬本與視窗分離**。資料庫保存不可變、全量的正史；對話視窗只是當前視圖，可以做「換水」與裁切。長期記憶提取應從原始賬本讀取，而不是從已被壓縮的對話殘骸再次摘要，避免壓縮誤差層層傳染。

第三個核心是**近況用推的，回憶用拉的**。熱橋負責把其他視窗剛發生的新對話直接補進當前視窗；基線由換水時建立的補給快照維持；真正較遠的歷史才由召回系統檢索。這個分工比一直補時間詞、擴大向量召回或提高 top-k 更直接地解決多視窗接續問題。

第四個核心是**結構閘門優先於提示詞**。Riverbend 不把「不要幻覺」視為有效防線，而是透過來源標示、說話者與日期邊界、排除系統信封、清除高風險歷史思考鏈、同窗鄰接取樣、衝突時要求確認等機制，直接降低錯誤歸屬與錯誤延續的機率。

第五個核心是**誰有權寫入記憶**。來源把「機器只搬運、模型或人依角色負責真正的書寫與升級」視為重要設計原則；同時強調多視窗共用交接檔時要有單一寫者，否則很容易出現晚寫覆蓋先寫的競爭問題。

## 架構與技術

Riverbend Repository 本身主要是方法論文件，並沒有可執行的主程式。README 明確說明「沒有安裝包」，主要內容集中在 `docs/memory-architecture.md`、`docs/casebook.md` 與未實作的 `appendix/river-design.md`。來源方法是在一台家用 Mac 上的自架 AI 系統中逐步長出來，但公開內容的重點是可移植的設計判準，而不是特定平台實作。

召回設計採 **BM25 + 向量檢索** 雙路並行。雙路先擴大候選池，再經融合重排與結構過濾，最後把少量候選交給輕量模型判斷真正相關的片段。為了補足「換個說法就撈不到」的問題，寫入端還會預先抽取具體錨點標籤，查詢時用標籤簇擴展候選池。時間詞則先用規則解析成日期範圍，不把這種結構性問題交給模型。

召回結果不是只回單句，而是會攜帶同一對話串內的前後鄰接內容，並附上日期、來源與說話者，降低模型拿半句話腦補場景的風險。近期自產內容則設有「新鮮度保險絲」，避免模型把自己最近說過的話反覆召回成新的敘事軌道；遇到明確的引用需求時再針對該查詢放行。

視窗管理部分把 token 視為主要容量尺度，bytes 只作為備援訊號。換水發生在回合邊界，會清理舊記憶頭、移除已沉澱內容、保留必要尾段與溢流，並驗證事件鏈是否仍能回溯到根。圖片等重資產則傾向在看過後換成原檔路徑占位，避免每輪重複支付上下文成本。

模型角色也刻意分級：敘事與日記使用品質最高的模型；召回裁判使用較小、可常駐預熱的模型；錨點抽取使用便宜的批次模型；時間解析、去重、索引與換水等結構操作則盡量不使用模型。整體原則是「生成敘事的用最好的、做判斷的用最小的、能不用模型的就不用」。

## 主要功能

這個 Repository 提供的不是執行功能，而是一組可以拆解實作的系統能力與工程判準：

- **三層長期記憶設計**：區分每輪常駐、按需召回與沉底保存的資訊。
- **多視窗連續性**：透過賬本、換水、交接與熱橋處理不同對話窗之間的接續。
- **混合召回**：BM25、向量檢索、錨點標籤、時間篩選與小模型裁判共同完成候選擴展與決選。
- **深回憶檔位**：把每輪快速召回與主動考古分成兩套預算，避免日常反射太慢、深查又不夠深。
- **結構式防幻覺**：在檢索、來源歸屬、歷史注入與衝突仲裁層設置硬邊界，而不是只依賴提示詞提醒。
- **檔案式跨窗記憶**：以一檔一記憶、索引、交接檔、備份與單一寫者等方式建立可讀、可回退的持久層。
- **成本與維運判準**：把 token、延遲、索引重建、模型分工、備份與隱私責任都納入系統設計，而不是只談召回準確率。
- **未實作 MCP 介面草案**：附錄設計 `wake()`、`recall()`、`remember()`、`handover()` 四個工具，展示如何把方法論翻譯成跨視窗記憶服務，但作者明確標示此設計未實作且不維護。

## 技術亮點

最值得保留的是**用失敗病例長出架構，而不是先畫理想架構再硬套**。文件中的閘門、快取策略、熱橋、換水與保險絲幾乎都對應實際遇過的錯誤，並多次記錄「原本看起來合理、量了之後拆掉」的機制。這種「先量再設計、閘門隨病蓋」的做法，比單純列一份長期記憶最佳實務更有工程價值。

第二個亮點是**把近期連續性和歷史回憶分成不同資料流**。多數記憶方案會想辦法把所有內容都塞進同一套搜尋；Riverbend 明確指出剛發生的跨窗內容不應該和幾週前資料一起競爭排序，因而用推送處理「剛剛」、用召回處理「更早」。這是很清楚的延遲與語意分層。

第三個亮點是**fail-open 不是單純容錯口號，而是先做結構過濾後才允許退化**。例如裁判逾時時可退回候選，但退回的是已經通過來源、回音、寒暄與其他硬閘門的結果，不是把裸 BM25 前三名直接塞進提示詞。這使「記憶壞掉時聊天仍能繼續」和「不要因降級而大量注入雜訊」同時成立。

第四個亮點是**原文、壓縮與權威層次分離**。原始賬本保持完整，摘要只服務當前注意力；同時把「眼前的人 > 紀錄 > 模型自己的印象」設成使用記憶時的權威順序。這種區分能降低長期摘要在多年累積後反客為主的風險。

第五個亮點是**把記憶寫入權當成系統設計問題**。誰能修改自畫像、誰負責日記、誰能升級永久記憶、誰只能搬運，會直接影響角色自主性、資料可信度與併發衝突。這比只討論向量資料庫或 embedding 模型更接近真正長期 Agent 的治理問題。

## 限制與風險

第一個限制是 **Riverbend 不是可直接執行的產品**。Repository 目前主要提供方法論、病例與設計稿，因此不能把文件中的效果直接等同於一套可複製安裝的系統。要落地仍需自行映射到既有聊天平台、資料庫、工具與生命週期。

第二個限制是 **多數門檻來自單一自架系統的實測**。例如換水水位、候選數量、尾段預算、裁判延遲與新鮮度區間都有具體數字，但文件本身也反覆提醒不要照抄；不同模型、tokenizer、對話型態與喚醒頻率都可能讓最佳值完全不同。它提供的是判準與測量方法，不是通用參數表。

第三個限制是 **缺乏正式跨系統基準測試**。來源有大量真實病例與量測紀錄，但不是標準化 benchmark，也沒有和其他記憶框架做控制變因比較。因此適合做架構研究與原型設計參考，不宜把局部實跑結果當成普遍效能結論。

第四個限制是 **部分邊界仍被作者明確列為已知缺口**，例如 retry 已經被日記游標處理過的舊回覆時，正史與日記可能短暫不一致；某些溢流與跨窗可見性問題也需要事件驅動補灌。這些揭露提升文件可信度，但也表示實作時仍需要自己的故障模型與測試。

第五個風險是 **自架記憶代表自己承擔資料治理責任**。長期對話通常是高敏感資料；本機部署雖可降低第三方暴露，但備份、權限、金鑰、網路出口與對外注入內容仍需自行管理。文件也明確把 token 成本、維護與 3-2-1 備份視為長期水電費的一部分。

附錄的 `river` MCP 設計目前是**未實作且不維護的草案**，不應當成現成的 MCP server。Repository 採 CC BY 4.0 授權，方法論可以分享、改作與商用，但需要標明出處。

## 與你的相關性

依公開技術 Profile，Riverbend 對 **LLM / Agent** 與 **SillyTavern / AI RPG** 都屬核心相關，因此兩項都評為 5。它直接處理長期角色記憶、跨 session 連續性、召回、人格與事實常駐、來源歸屬與角色自主寫入權，和長期 AI 角色／伴侶系統最困難的幾個問題高度重疊。

對 **AI R&D** 也評為 5。它提供的不只是架構描述，還包含延遲量測、上下文容量、召回失敗案例、索引更新策略、候選融合、錯誤歸因與已知缺口，很適合拆成記憶品質、召回準確率、連續性與幻覺率的實驗題目。

對 **AOI × AI** 評為 1，因為來源不涉及電腦視覺、瑕疵檢測或製造資料管線；若未來建構具有長期任務記憶的工業 Agent，其記憶架構才可能間接借用。對 **Image Generation** 也評為 1，文件只把圖片當成上下文中的重資產處理，並沒有影像生成能力。

整體 `overall` 評為 5，主要原因是它在公開 Profile 的 LLM／Agent 與 AI RPG 交集上，提供了非常具體且帶失敗經驗的長期記憶設計材料，而且和一般只談向量搜尋的記憶方案形成明顯互補。

## 建議怎麼使用

- `BUILD`：不要一開始照抄完整三層水利工程。先盤點自己的視窗數、上下文生命週期與真正失憶點，再依文件建議從「瘦的睜眼層 → 檔案記憶＋索引 → 關鍵字搜尋」建立最小版本。只有真實查詢顯示需要時，才逐步加入向量召回、錨點、裁判與更多閘門。
- `LEARN`：優先讀 `docs/memory-architecture.md` 的三層架構、窗口管理、召回、防幻覺、筆的分工與代價，再用 `docs/casebook.md` 對照每條規則是被什麼實際錯誤逼出來的。閱讀時重點應放在「為什麼會拆掉某個機制」而不只是最後留下什麼。
- `REFERENCE`：把 Riverbend 當成長期 Agent 記憶設計的病例型參考。之後評估其他記憶方案時，可以固定檢查：原文是否保留、近期與歷史是否分流、召回失敗是否會阻斷主流程、來源與說話者是否可追溯、寫入權如何治理、摘要是否會覆蓋原始真相、以及是否有真正的回退路徑。

如果要把方法直接轉成自己的設計文件，最值得先抽出的三句判準是：**先數窗再設計、近況用推的而回憶用拉的、閘門隨病蓋**。這三條比照抄某個 top-k、token 門檻或 MCP 介面更可移植。

## 與其他收藏的關聯

- [A Simple Nest](./github-cynthianani-a-simple-nest.md)：兩者都來自長期 AI 伴侶系統的實作經驗，也都把記憶拆成常駐上下文、召回、持久層與壓縮生命週期。A Simple Nest 更像從零建構 stateful companion runtime 的分章工程筆記；Riverbend 則更集中在多視窗長期記憶、注意力分層、失敗病例與防幻覺判準。
- [ai-memory](./github-akitaonrails-ai-memory.md)：兩者都強調長期記憶不該只是 `embed → top-k → inject`。`ai-memory` 是可執行、面向 Coding Agent 的跨 Agent memory runtime，具有 Git wiki、SQLite、hooks 與 hybrid retrieval；Riverbend 則是 AI 伴侶情境下的方法論與病例集。前者適合看完整產品化實作，後者適合看哪些設計決策是被真實失敗逼出來的。

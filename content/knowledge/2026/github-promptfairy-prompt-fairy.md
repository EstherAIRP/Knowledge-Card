# prompt_fairy｜胖譜小精靈

## 一句話介紹

胖譜小精靈是一個以瀏覽器本機資料為核心的 AI 圖像提示詞工作台，把「貼入既有提示詞、替換角色、套用常用片段、檢查衝突、生成新版、保存版本」整理成一套可反覆操作的流程。

## 它解決什麼問題

影像生成的提示詞很容易累積成長文字：角色外觀、服裝、場景、鏡頭、風格、負面詞與參考圖規則彼此混在一起。當使用者想保留大部分構圖，只替換人物或局部風格時，直接手改容易漏掉衝突描述，也不容易管理曾經使用過的版本。

胖譜小精靈把這個問題拆成幾種可重用資料：角色卡保存人物本身，咒語匣保存常用提示詞片段，胖譜庫保存完整提示詞與版本紀錄，工作台則負責單次解析、置換與輸出。這讓提示詞不再只是一次性文字，而是可組裝、可保存、可回頭修改的個人工作資料。

## 核心概念

- **本機優先（local-first）**：目前穩定版將應用狀態寫入瀏覽器 `localStorage`；角色、咒語、胖譜、設定與 API key 都由使用者裝置保存。產品規格也把圖片與版本紀錄的本機保存列為核心方向。
- **分離人物、片段與完整提示詞**：角色卡、咒語匣、胖譜庫各自管理不同粒度的資料，避免把所有設定永久綁在單一提示詞。
- **局部置換而非整段重寫**：工作台可對人物、服裝、場景、動作、風格、比例與負面詞選擇「原樣保留、套用角色卡、小精靈救救我、我自己來」。
- **本機規則 + 遠端模型雙路徑**：基本解析與衝突提醒可在前端以規則完成；需要模型改寫時，可直接呼叫 OpenAI 或 Gemini API。API 呼叫失敗時，程式會退回本機整理版。
- **保守傳送資料**：產品規格預設送出前確認，並明確區分這次送給模型與不送出的資料；目前生成流程也只組合選中的文字資料，不主動上傳圖片或整個胖譜庫歷史。

## 架構與技術

目前 Repository 是偏輕量的前端 PWA：

- 主要實作由 `index.html`、`app.js`、`styles.css` 組成，沒有獨立後端。
- `manifest.webmanifest` 將應用定義為 `standalone` PWA，語系為 `zh-Hant`。
- `sw.js` 快取應用殼層與主要靜態資源，導覽請求在離線時可回退到 `index.html`。
- 穩定版狀態以單一 `prompt-sprite-state-v2` 鍵存入 `localStorage`。
- 本機解析器使用文字規則判斷單人／雙人／多人、常見長寬比與負面詞，並針對遮擋、柔焦／底片與負面詞衝突等情況產生提醒。
- OpenAI 路徑呼叫 `POST /v1/responses`；Gemini 路徑呼叫 `generateContent`。模型名稱由設定頁保存，並提供連線測試。
- Repository 另保留 `_experiments/local-rule-engine/` 規則引擎實驗版，和根目錄穩定版並存以便比較。

資料模型文件進一步規劃 `settings`、`characters`、`phraseCards`、`promptEntries`、`promptVersions`、`assets` 等集合，但也明確說明資料庫實作尚未綁定 IndexedDB、localForage 或 Dexie；因此應把這份文件視為資料模型設計，而不是全部已落地的儲存層事實。

## 主要功能

- **工作台**：貼入原始提示詞、選角色、選擇各欄位的改寫方式、套用咒語、產生新版提示詞。
- **角色卡**：保存角色外觀、固定標記／配件與寫入提示詞的偏好；目前穩定版工作台設有兩個角色選擇槽，映射為 `[AA]`、`[BB]`。
- **咒語匣**：保存臉部參考、光線、人物質感、負面詞、限制與風格等可重用片段，並附帶一組預設咒語。
- **胖譜庫**：收藏完整提示詞，保存來源、工具、狀態與版本資料，並可重新送回工作台使用。
- **衝突提醒**：以規則檢查固定標記可能被服裝遮住、底片／柔焦風格與負面詞互相抵消等情況。
- **AI 改寫**：可使用 OpenAI 或 Gemini，把角色卡、欄位模式、咒語與原始提示詞組合成改寫請求。
- **本機備援**：未連 AI 或 API 失敗時，仍可用本機規則與片段組裝出整理版提示詞。
- **資料管理**：設定頁支援本機資料匯出／匯入與清除；PWA 可安裝並快取主要介面資源。

## 技術亮點

最值得參考的不是「再做一個提示詞編輯器」，而是它把影像提示詞視為可維護的結構化工作流程。

第一個亮點是資料邊界清楚：人物的長期設定、可重用語句、完整作品提示詞、單次工作狀態分開管理。這種切法比把所有資訊塞進一個模板，更適合反覆換角色、換風格與建立系列作品。

第二個亮點是把確定性規則與生成模型分工。本機先處理可明確判斷的比例、人物數量與簡單衝突，模型只負責需要語意改寫的部分。這種做法可以降低不必要的 API 依賴，也讓離線／無 key 情境仍保有基本功能。

第三個亮點是對資料傳送範圍有明確產品設計。即使目前實作仍是純前端，送出前確認、預設不送圖片、不送歷史紀錄等原則，對個人影像工作流很實際。

## 限制與風險

- **授權不明**：GitHub Repository 目前沒有宣告 license；若要複製、修改或整合到其他公開／商業專案，應先確認作者授權。
- **API key 儲存在 `localStorage`**：這比把 key 寫進 Repository 安全，但仍不是高安全性祕密儲存。任何能在同源頁面執行的惡意腳本都可能讀取；公開部署時尤其要注意 XSS、第三方腳本與供應鏈風險。
- **瀏覽器直接呼叫模型 API**：沒有後端代理可以集中做金鑰隔離、額度控管、審計與請求政策；也可能受到供應商 CORS、模型可用性或 API 變更影響。
- **目前儲存層偏早期**：穩定版把整體狀態放在 `localStorage`，若大量保存圖片或版本資料，容量與效能會成為瓶頸；資料模型文件雖規劃更完整的 `assets`／版本結構，但尚不等於已完成 IndexedDB 等儲存實作。
- **本機解析屬啟發式規則**：人物數、比例、衝突檢查依賴關鍵字與正規表示式，對複雜提示詞、多語言描述或特殊語法的覆蓋有限。
- **規格與實作可能不同步**：Repository 同時保存產品規格、資料模型、穩定版與實驗版；評估功能時應以目前程式碼為準，不應把文件中的 MVP／後續規劃全部視為已完成。
- **專案仍很年輕**：Repository 建立於 2026 年 7 月，2026 年 8 月底仍持續推送更新；在正式整合前，仍應自行驗證資料相容性與 API 行為。

## 與你的相關性

依公開技術背景，這個專案對 **Image Generation** 的相關性最高：它直接處理生成提示詞的整理、角色一致性、重用片段、版本追蹤與 OpenAI／Gemini 工作流，適合作為個人影像生成工具的產品與介面參考。

對 **AI R&D** 的價值主要在「規則先行、模型補位」與本機優先工作流設計，而不是模型研究本身。對 **LLM／Agent** 則屬間接參考：目前沒有 Agent 編排或工具調用框架，但它示範如何把可確定規則、使用者覆寫與模型改寫切成不同責任層。

它與 AOI／Computer Vision 的直接關聯低；若未來要研究人機協作式的視覺工作流、提示詞資產管理或可重現的生成實驗紀錄，資料拆分方式仍可借鏡。

## 建議怎麼使用

- **TRY**：如果日常會反覆改寫人物、風格或參考圖提示詞，可以直接體驗工作台，觀察角色卡／咒語匣／版本紀錄是否真的降低重複編輯成本。
- **REFERENCE**：特別值得參考本機優先前端產品如何切分提示詞資料、如何用簡單規則承擔可確定判斷，以及如何在純瀏覽器架構下設計「送出哪些資料」的隱私介面。

若要實際長期使用，建議先把它視為個人工作台而不是成熟的跨裝置資產系統；大量圖片、多人共用、同步、後端金鑰隔離與更完整的版本資料庫都還需要額外工程。
